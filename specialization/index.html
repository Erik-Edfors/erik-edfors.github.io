Details

For my specialization, I decided to make a multiplayer game. A card game to be more precise. In this game, you can set up a server and play a simple card game with anyone over the internet.

Whilst it might sound simplistic. It is anything but. Multiplayer games are notoriously difficult to get right. But even so, I really wanted to learn how to.

Why

For some years now I have had the idea to make a game for me and my friends to play around with. I wanted to make a game in which I could make any changes I wanted. To really customize the game for my and my friends.

This project, especially in conjunction with the completion of my network communications course, felt like the perfect moment to make it happen.

While I have some personal reasons for why I wanted to make this project. I also felt that it would be a great way to deepen my knowladge of network communications and to get some practical experience in making a multiplayer game.

Gameplay

In this game, each player takes turns playing cards. Each player begins the game with 10 Health Points (HP) and 0 Resource Points (RP). Players draw 3 cards from their deck at the beginning of their turn. Then they can play any number of cards they can afford, before passign their turn to the next player.

From this, and with the cards below inside each players deck, an entire game can be played.

A typical game sees both players playing Resource cards to start generating RP. Then they start playing Damage cards to deal damage to their opponent until they reach 0 HP. Then the game is over.

Shields, Destroy and Sacrifice cards make the game a little less predictable, allowing players to stratagize and interfere with eachother more.

Setting Up a Game

To play my game, you and a friend will need to download the release from my GitHub. Then you both will need to unzip the .zip file. Now you can launch the Client .exe file inside. One of you will also need to launch the Server .exe file.

Depending on if you are playing on the same network as your friend or on different networks, you may have to do additional setup to play.

Playing on the same network

When playing on the same network, you will need to remember the port you gave the server on setup. Give this port to your friend along with your local IP address (can be found by using typing ipconfig in the command prompt and reading the ipv4 address field). Your friend will have to add this address and port to their server list.

You do not need to input your own IP Addres. Instead you can use “localhost” to indicate the server is located on the same computer. Localhost will also already be on the server list by default.

Playing on different networks

To play on different networks, whoever is hosting the server will have to make a Port Forward on their router. Most routers have an online guide on how to do this. You will need to port forward the port you wish to use for the server. I recommend using the default port visible when first starting the server.

After having made the port forward, you will need to give your friend yout public IP Address (Can be found using whatismyip.com or other similar websites) and the Port you gave the server. You can connect to the server using the same, but you can also use “localhost” instead of your IP Address if the server is on the same computer.

When you have set up the server and both you and your friend have connected to it, you can start the game from the server window. Then you can play!

Implementation

Here I will explain some of the implementation process for this project. While the entire project is too large to describe succinctly here, I will describe the design and challanges I encountered when implementing multiplayer specifically.

Networking

To make a multiplayer game, the game needs to be able to send data to another computer so they can synchronize their gamestates. For a card game, this means sending information about which cards are played, moved, destroyed and other things, like a players health changing. This is to make sure that one player doesn’t see one gamestate (for example a player still being alive), and the other player sees another (a player being dead).

But first the game needs to be able to communicate. For this i used the Winsock2 API for windows. This is an API for sending data over the internet. Over this I created a library for creating clients and servers, objects that handle connections and sending information.

Clients and Servers are both NetworkManagers. A NetworkManager being a class I made to manage sending and recieving data and converting it to formats more readable for my programs. The network manager takes messages, serializes them into a binary format, and then attaches it, along with additional information, to a network message which can then be sent to a remote.

The format of network messages I decided should include an type id, checksum and assured flag. The type id allows the reciever to what kind of data is being sent. The checksum allows knowing if the message has been changed since being sent. The assured flag indicates if the sender expects a confirmation of recieval from the remote. This allows for secure communication where both the sender and reciever can know for certain that the correct message has been recieved.

Game State

In this project, gamestate is a centerpoint. The gamestate represents the state of the game, and both the server and clients contain a gamestate.

The server is the one with THE gamestate, and each client needs enough information from the server to recreate it perfectly on their own computers.

To solve this, I made it so each client and server has a Game object which contains the game state. The state of the game can only change by sending the Game object a Command. A Command is an instruction for the Game object to change the gamestate in a deterministic fashion. This way, if two different Game objects recieve the same commands, in the same order, their game state will allways be identical.

Using this system, when a player wants to do anything in the game, the client interprets the input from the player (like clicking a card) into a request (play a card, select a target, etc…), which is then sent to the server. The server looks at the request, checks if it is valid, and then converts it into a command which is applied to its Game object. This command is then also sent to each client to apply to their own Game objects. This means that any action a client takes, the server makes a command out of, and sends to each client to apply to their game objects, making sure each game state is identical between clients and server.

This model however has an issue. In many games a server doesn’t want a client to know the full gamestate. Cause if it does, then a cheated client can see things it shouldn’t be able to. This is unfortunately true for my game as well. A client can be cheated to reveal information, like which cards an opponent has on hand, and which cards each player will draw. To fix this, I whould have to make it so the server doesn’t reveal a card before a client should be able to see it. This however whould mean that clients would have a different game state than the server. This can cause identical commands to act differently, eventually resulting in the client and server not having even remotely close to the same game state. This is solvable, so I plan on making it so in the future But for now, I highly doubt my game is going to have hackers anytime soon.
